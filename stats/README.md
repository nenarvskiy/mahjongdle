# Статистика системы очков v4

`scorestat.py` — прогон системы v4 в пяти режимах:

* **`--mode discard`** (по умолчанию) — идеальный сброс: для случайной 14-тайловой
  руки (плюс индикатор доры, индикатор урадор и ветра дня) перебираются все
  ≤14 сбросов, и выбирается тот, что даёт максимум итога (база + структуры + яку).
* **`--mode complete`** — проверка ИСХОДНОЙ руки: готова ли 14-тайловая раздача
  как есть и сколько она стоит (аналогично обычная / манган / ханеман / …).
  См. раздел «Режим 2: готовые руки».
* **`--mode design`** / **`--mode design-complete`** — только дизайн-частоты
  (состояние × тир и строка «Готовая рука») в формате `maj_stat`, нужные для
  пересчёта цен базы по K/P. См. раздел «Пересчёт базы по K/P».
* **`--mode yaku`** — только структуры и яку, **без шантенов** (значит и без
  тира, базы, дор, ака, риичи и урадор — они считаются по хану). Лучший сброс —
  по максимуму суммарных очков (структуры + яку) на 13 тайлах. В ~12 раз быстрее
  режима 1 при той же точности — для частот очень редких яку (большие ветра и
  т.п.). См. раздел «Режим 5: только яку».

Что считается для каждой 13-тайловой руки после сброса (режим 1):

* **состояние** — шантен по концепту игры (`src/shanten.js`): 2-шантен / 1-шантен / тенпай;
* **тир** — по хану лучшей руки, достижимой за минимальное число добора
  (риичи +`rules.riichiHan`, цумо нет, дора и ака считаются, фу не считаются,
  манган = 5+ хан); ака — как в игре: в стене по одному красному тайлу на масть,
  пятёрка масти красная с вероятностью n/4 (n — число пятёрок масти в руке),
  +1 хан за каждый красный вид, оставшийся в победной руке;
* **ура-доры** (`rules.uraDora`, по умолчанию включены; `--no-ura` отключает) —
  индикатор урадор берётся из мёртвой стены, поэтому он **не участвует в
  решении**: по нему нельзя выбирать сброс, тир, структуры и яку. Модель
  двухэтапная, как в игре:
  1. **решение** — сброс, целевая рука, тир, структуры, яку считаются по хану
     **без** урадор (именно этот хан видит игрок в момент сброса);
  2. **финальный счёт** — после открытия урадор лучшая рука ищется **заново**,
     уже с урадорами (`analyze` возвращает и `best` без урадор, и `best_fin`
     с ними; очки/база/итог отчёта считаются по `best_fin`). Якуман урадоры
     не получает — как и дору (это делает сам `eval_regular`/`eval_chiitoi`);
     если урадора в победной руке нет, второй пересчёт не запускается (тот же хан);
* **база** — таблица `3 × 6` (состояние × тир) из конфига;
* **структуры** — лучшее разбиение 13 тайлов на паттерны v4 (DP по мастям);
* **яку** — яку v4, выполняющиеся на 13 тайлах.

Все числа берутся из `config/scoring.json -> systems.v4`. В коде стоимостей нет:
цены структур/яку, таблица базы, пороги тиров и правила читаются из конфига.
Проверено на практике: меняешь цену в конфиге — меняется отчёт (`--config`).

Команды ниже используют `py` — это лаунчер Python в Windows (на других системах
`python3`); модуль `numba` обязателен (без него всё работает, но в десятки раз медленнее).

## Запуск

```powershell
py stats/scorestat.py -n 20000 --quick            # 20k рук, один процесс
py stats/scorestat.py -n 1000000 -w 12            # миллион рук, 12 процессов
py stats/scorestat.py -n 1000000000 -w 12         # миллиард рук (ночь)
py stats/scorestat.py --config other.json -n 20000 --quick   # другой конфиг
py stats/scorestat.py --mode complete -n 1000000000 -w 12    # режим 2: готовые руки
py stats/scorestat.py --mode design -n 100000000 -w 12        # частоты базы (K/P)
py stats/scorestat.py --mode design-complete -n 10000000000 -w 12   # строка «Готовая рука»
py stats/scorestat.py --mode yaku -n 200000000 -w 12          # только яку, без шантенов
py stats/scorestat.py --mode yaku --raw -n 1000000000 -w 12   # частоты яку на 14 тайлах
```

Флаги: `-n` рук, `-w` процессов,
`--mode {discard,complete,design,design-complete,yaku}`, `--seed`, `--chunk`,
`--out` каталог для результатов (по умолчанию `stats/out/last`), `--no-riichi`,
`--no-aka`, `--no-ura`, `--quick` (без пула), `--partition-check HANDS_JSON`
(очки разбиения для списка рук), `--raw` и `--no-greedy` (только для `--mode yaku`).

## Яку v4: плоские очки

Плоское яку v4 — это **свойство текущего состава** (13 тайлов после сброса, в
режиме 2 — все 14 тайлов готовой руки). Готовность руки и «достижимость за добор»
**не проверяются**: засчитывается сам факт наличия структуры/свойства — ровно так
же, как структуры считаются по лучшему разбиению 13 тайлов. Якуман по хану
(`eval_regular`) — отдельный механизм; ура-доры и доры он не получает, как и плоские яку.

от настоящего сансёку доккоу: 9 рангов × вероятность трёх троек ≈ 3.15·10⁻⁸
против 3.5·10⁻⁹ у дайсангена). Теперь семантика совпадает с названием, а большие
драконы — отдельный яку `daisangen`. Заодно добавлены семь яку из запроса
(рянпейко, большие драконы, малые/большие ветра, только хоноры/терминалы/зелёные).

История (2026-10-23): **мультисаунды ценных + «сильный гасит слабый»**.
Раньше ценные яку (yakuhai_pon/valuable_pair/valuable_tile) срабатывали булевым
«хотя бы один», и один пон дракона давал все три ступеньки подряд (870+60+15
за пон; 60+15 за пару), а две пары ценных считались как одна. Теперь: каждый
вид ценного тайла (драконы + ветер раунда + ветра места) засчитывается только
на своей самой высокой ступеньке — 1 тайл = «1 ценный тайл», 2 = «пара ценных»,
3–4 = «якухай (пон ценного)» — а разные виды суммируются (две пары = 2 × 60,
два пон = 2 × 870). Плюс правило «сильный яку гасит очевидно включённый слабый»:
`ryanpeikou` гасит `iipeikou`, а `sanankou` не засчитывается, когда его тройки
«внутри» `daisangen` / `daisuushi` / `shousuushi` / `sanshoku_doko` (дайсанген
«это просто дайсанген», без малых и без сананко). `designFrequencies` ценных
пересчитаны под новую семантику: p теперь = ОЖИДАЕМОЕ число инстансов на
14-тайловую руку (1.44005 / 0.23401 / 1 из 63.2), точной комбинаторикой
(старые 0.8892 / 0.23105 / 1 из 63.4 — семантика «хотя бы один» — воспроизведены
этой же формулой с 4 знаками, модель проверена).

## Режим 5: только яку (`--mode yaku`)

Проверка частот редких яку без самой дорогой части режима 1 — шантенов
(`shanten_fast` + `analyze`, которые нужны только для тира/базы). В этом режиме:

* считается только **структуры + яку** на 13 тайлах после сброса;
* **лучший сброс** — максимум суммарных очков (структуры + яку), без шантенов;
* нет тира, базы, дор, ака, риичи и урадор (они считаются по хану, а хан — по шантену);
* отчёт: по каждому яку — рук, % рук, «1 из», очки/рука, всего очков; то же по
  структурам; итог и гистограмма очков.

Ускорение без потери точности (флаг `--no-greedy` отключает, это эталон для
сверки): разбиение (ДП) считается не для всех сбросов, а только для тех, что
могут выиграть — сначала по всем сбросам дёшево считаются яку, и сброс
отбрасывается, если он отстаёт от лучшего по яку больше чем на безопасную
границу суммы структур на 13 тайлах (7 × максимальная цена блока; блоков в 13
тайлах не больше 6). Проверено: `--mode yaku` и `--mode yaku --no-greedy` дают
**побитово одинаковые** `components.csv` и `score_hist.csv` (200 000 рук, seed 1).

`--raw` — ещё быстрее и без сброса: свойства считаются на самих 14 тайлах
(частота яку «как есть», дизайн-базис `designFrequencies.yaku`), ДП не считается
вообще. Одинаковые руки тут не «играются», поэтому `--raw` годится только для
частот яку, а не для очков.

### Почему джекпоты так и остаются недостижимыми

Сброс выбирается по очкам **текущего** 13-тайлового состава. Пока до якумана не
хватает тайла, он не даёт ничего сверх обычных структур, поэтому «добирать» его
сбросом невозможно: режим `yaku` — честная имитация, а не охота за джекпотом.
Отсюда практические частоты ≈ случайные (точные значения — комбинаторика на
C(136,13), см. `design/scoring-v4.md`):

| яку | 1 из (13 тайлов) | рук нужно для 10 срабатываний (12 процессов) |
|---|---|---|
| большие драконы | 786 142 549 | ~7.9·10⁹ (13 ч) |
| только хоноры | 12 920 583 539 | ~1.3·10¹¹ (9 сут) |
| малые ветра | 43 561 441 987 | ~4.4·10¹¹ (1 мес) |
| только терминалы / зелёные | 193 808 753 087 | ~1.9·10¹² (4.5 мес) |
| большие ветра | 15 617 721 983 648 | ~1.6·10¹⁴ (31 год) |

Поэтому для проверки самих яку надо брать `--raw` (2.3 млн рук/с одно ядро,
9.9 млн на 12): 1e9 «сырых» 14-тайловых рук — это ~2 мин, а не 17 ч.

## Режим 2: готовые руки (`--mode complete`)

Проверяет, готова ли исходная 14-тайловая раздача (до любого сброса) и считает
её стоимость по пути готовой руки игры (`src/evaluate.js -> evaluateComplete`):

* **готовность** — как `isWinningHand`: стандарт (пара + 4 мендзена), чиитоицу
  (7 пар), кокуши (все 14 тайлов — из 13 видов, 13 видов + пара); рука может
  быть двух типов сразу — берётся лучшая по хану;
* **хан** — стандарт: максимум по ВСЕМ разложениям (как `allDecompositions` в
  игре), чиитоицу: 2 + таняо/хоницу/чиницу + ака/дора/ура, кокуши: 13;
  в игре нет яку-мана у чиитоицу (чинрото-чиитоицу = 5 ханов, не 13);
  риичи +`rules.riichiHan` по общему дефолту (та же «идеальный игрок»-конвенция,
  что в режиме 1 — потенциальные достройки игры тоже оцениваются с риичи;
  `--no-riichi` отключает), пинфу нет (нет выигрышного тайла),
  цумо отключён правилами;
  дора, ура-дора и ака дают хан только если есть хотя бы один хан-яку — разложение
  без яку игра пропускает; поскольку риичи — хан-яку, «бессе яку» теперь
  1 хан (riichi), а не han −1;
* **ура-доры** — индикатор урадор дилуется рядом с индикатором доры: готовая
  стартовая рука — это состояние «после решения», урадоры уже открыты, поэтому
  в этом режиме они входят в хан сразу (в отличие от режима 1). Якуман
  урадоры по-прежнему не получает;
* **база** — строка «Готовая рука» таблицы базы (последняя строка) со своим
  тиром: в конфиге 2× строки «Тенпай» — тенпай уже платит полную
  потенциальную стоимость тира, готовая рука добавляет «гарантию»
  (нет сброса, нет риска, все 14 тайлов работают); flat-бонуса
  `completeBonus` больше нет (строка — единственный источник базы);
* **структуры и яку v4** — считаются по всем 14 тайлам руки;
* **ака** — та же модель, что в игре: в стене по одному красному на масть,
  пятёрка масти красная с вероятностью n/4; дора — индикатор +1.
  Измерено на 1e10 раздач (30 377 готовых рук): P(рука без красных | готова) =
  0.6504, E[красных | готова] = 0.39; распределение
  красных: 0 — 65.04%, 1 — 30.46%, 2 — 4.32%, 3 — 0.17%.

Проверка выбора строки «Готовая рука» = 2× тенпай (по прогону 10b после пересчёта
2026-10-17, с дефолтным риичи и урадорами): тиры готовых рук — Normal 27 191,
Манган 2 119, Ханеман 963, Байман 91, Санбайман 1, Якуман 12 (из 30 377 готовых);
вклад строки в EV на раздачу ≈ **0.728** (по ячейкам: 0.120/0.081/0.067/0.060/
0.024/0.377), это ≈ 240 000 очков базы на готовую руку; полный средний счёт
готовой руки 264 949 (структуры+яку добавляют ≈0.075+0.001 на раздачу).
Доли тиров внутри EV базы готовых: Normal ~16%, Манган ~11%, Ханеман ~9%,
Байман ~8%, Санбайман ~3%, Якуман ~52%.

Готовых рук мало: P = 3.0377·10⁻⁶ (измерено на 1e10 раздач: 30 377 готовых,
~1 из 329 196; их тиры: Normal 89.51%, Манган 6.98%, Ханеман 3.17%, Байман 0.30%,
Санбайман 0.003%, Якуман 0.040% — это уже с риичи и урадорами, т.е. финальные
тиры), поэтому режим оптимизирован под большие N: отсев «не готова» —
парой быстрых проверок (остатки сумм мастей mod 3 + поны хоноров) до того, как
запускать DFS.

```powershell
py stats/scorestat.py --mode complete -n 20000000 --quick          # ~5 c, 1 процесс
py stats/scorestat.py --mode complete -n 1000000000 -w 12          # ~3000 готовых рук
py stats/scorestat.py --mode complete -n 10000000000 -w 12         # ~30 000 готовых рук
```

Ориентиры по N (P = 3.04·10⁻⁶ из 1e10; ~2.5 млн раздач/с на ядро, отсев дешёвый):

| N | готовых рук (ожидаемо) | время, 12 ядер |
|---|---|---|
| 1e8 | ~300 | ~3 с |

Редкие типы (измерено на 1e10): чиитоицу (с двойными руками) 11.59% готовых;

В этом режиме колонка «EV-дизайн» сравнивает с частотой `design-complete`
(её измеряет `--mode design-complete`), поэтому `радио` по базе выходит ровно

Случайные величины — два независимых SplitMix64-потока: раздача (14 тайлов +

и «независимые» числа из того же потока коррелировали бы с рукой; отдельное
состояние устраняет корреляцию). Микс SplitMix64 в горячих циклах инлайнится
(не через вызовы хелпера): numba на этой версии бито сзывает результаты
повторных вызовов одного @njit-хелпера из разных мест тела функции —
проверено и обход задокументирован в `scorestat.py` (комментарий у
`_splitmix64`). Примечание: микс в знаковом int64 (арифметические сдвиги) —
поток не идентичен каноническому беззнаковому SplitMix64, но эмпирически
валиден (2026-10-22: частоты всех 34 видов, младшие биты z и редкие типы
рук — все в пределах 1.6 sigma от точной комбинаторики; перевод на uint64
не сделан ради воспроизводимости по seed).

## Пересчёт базы по K/P

Таблица базы в конфиге — это **одна шкала редкости**: цена ячейки
`состояние × тир` = `K / P`, где `P` — вероятность ячейки за раздачу (доля),
а `K` подобран так, что 2-шантен/Normal = 100: `K = 100 · P[2ш][Normal]`
(в `design_frequencies.json` `K` печатается в «процентных» единицах —
13.122162 = P в процентах, а `price_pure` считается по долям, это одно и то же
отношение). Плюс к чистым `K/P` в конфиге есть авторские «полы»: порядок тиров
внутри строки должен строго расти (`N < M < H < B < SB < Y`), а чистый `K/P`
его иногда нарушает (Якуман в данных ЧАЩЕ Санбаймана, поэтому `Y` считается
от `SB`, а не от своего `P`).

Актуальная политика (после пересчёта 2026-10-17, финальные правила):
Normal/Манган/Ханеман/Байман = чистое `K/P`; Санбайман = 0.9 × чистое `K/P`
(«подешевле»); Якуман = 1.33 × Санбайман (джекпот); строка «Готовая рука» =
ровно 2 × строки «Тенпай» (надбавка за гарантию). Прежние полы Haneman
(+13..21% к чистому) больше не нужны: под урадоры чистое `K/P` ханемана само
выше мангана. Полный разбор чисел — `design/scoring-v4.md`,
раздел «Пересчёт 2026-10-17».

Частоты `P` лежат в конфиге в `designFrequencies.base.values` (строки 0..2 —
13 тайлов после сброса; строка 3 — готовая стартовая рука). Их измеряют два
дизайнерских режима (структуры и яку не считаются, поэтому это в разы быстрее
обычного прогона):

```powershell
py stats/scorestat.py --mode design -n 100000000 -w 12 --out stats/out/design
py stats/scorestat.py --mode design-complete -n 10000000000 -w 12 --out stats/out/design
```

**Точность ячеек разная** — редкие тиры в дорогих строках на 1e8/1e10 почти не
набираются, и там цена держится на политике шкалы, а не на измерении:

| ячейка | событий | 1σ |
|---|---|---|
| 2-шантен / Normal…Байман (1e8) | 457 000 … 13 122 000 | ≤ 0.15% |
| 2-шантен / Санбайман (1e8) | 13 958 | 0.85% |
| 2-шантен / Якуман (1e8) | 32 471 | 0.55% |
| 1-шантен / Санбайман (1e8) | 566 | 4.2% |
| 1-шантен / Якуман (1e8) | 2 467 | 2.0% |
| Тенпай / Санбайман (1e8) | 10 | 32% |
| Тенпай / Якуман (1e8) | 27 | 19% |
| Готовая / Санбайман (1e10) | 1 | 100% |
| Готовая / Якуман (1e10) | 12 | 29% |

Поэтому Санбайман/Якуман заданы от политики (`SB = 0.9 × чистого K/P`,
`Y = 1.33 × SB`), а не от своего `P`: при чистом `K/P` их порядок
переворачивался бы (Якуман в данных чаще Санбаймана). Если нужны измеренные
(а не политические) цены хвоста, `--mode design` надо гнать на `N` на порядок
больше — 1e9 ≈ 18 ч на 12 процессах.

* `--mode design` — как в `maj_stat`: 14 тайлов, **лучший сброс по шантену**,
  тир — по лучшей достижимой руке; урадоры открываются после сброса, поэтому
  тир берётся **финальный** (с урадорами), а сброс — без них. Пишет
  `design_frequencies.json`: `P_counts` (абсолютные числа по ячейкам), `K` и
  `price_pure` (чистый `K/P`), и печатает таблицу (включая строку «>=3 шантен»).
* `--mode design-complete` — только готовые стартовые 14-тайловые руки
  (как `--mode complete`): `P(готовая)`, распределение готовых по тирам и
  `P(рука + тир)` для строки «Готовая рука». Пишет `design_complete.json`.

Порядок пересчёта при смене правил (так сделан пересчёт 2026-10-17 — включение
урадор и отключение цумо):

1. прогнать оба дизайнерских режима на большом `N` (для редких ячеек —
   не меньше 1e8, лучше 5e8; рядовая диагностика быстрая:
   `--mode design -n 100000 --quick` ≈ 40 с и уже даёт K);
2. взять `price_pure` из `design_frequencies.json` (это уже `K/P` с якорем
   2ш/Normal = 100);
3. наложить авторские решения — те же *относительные* отклонения, что в
   `design/scoring-v4.md` (SB: −10% к чистому, Y: 1.33 × SB, «Готовая» =
   2 × «Тенпай»), и проверить, что порядок `N < M < H < B < SB < Y` держится
   в каждой строке;
4. вписать новые `P` в `designFrequencies.base.values` и новые цены в
   `base.values` (плюс пояснения в обоих `note`);
5. после правки цен — перегенерировать фикстуры паритета
   (`gen_v4_reference.py`, `gen_complete_reference.py`) и прогнать `node --test`.

Важно: `analyze` трактует копии **обоих** индикаторов (доры и урадор) как
недоступные для добора (`maxc[ind] -= 1`, `maxc[ura_ind] -= 1`) — как в игре,
где эти тайлы лежат в мёртвой стене.

## Паритет игра ↔ статистика

Игра (`src/`) и статистика (`scorestat.py`) считаются по одной системе
(`systems.v4` из `config/scoring.json`), и их совпадение контролирует автотест:

```powershell
node --test test/v4-parity.test.js
```

Тест берёт 165 рук из `stats/fixtures/v4_eval_cases.json` (120 случайных из
`hands13.json` + 45 указанных: покрываются все состояния, все 6 тиров, кокуши,
чиитоицу, кан, все формы структур и красные пятёрки + 6 указанных с
ура-дорой — в том числе «якуман + ура-дора», где урадоры не должны добавляться;
с 2026-10-19 ещё 12 указанных рук на новые яку: рянпейко (в т.ч. перекрывающийся),
большие драконы, сёсанген-граница, малые/большие ветра, только хоноры,
только терминалы, только зелёные (+негатив с 9s), сансёку доккоу)
и требует побитового совпадения шантена, хана потенциала (решение, без урадор),
финального хана с урадорами, состояния, тира, базы, структур (счётчики
по каждому id), плоских яку и итога. Файл с эталонными оценками пересчитывается
Python-ядрами:

```powershell
py stats/tools/gen_v4_reference.py
```

Режим 2 (готовые руки) контролирует второй тест — `test/v4-complete-parity.test.js`:
619 рук из `stats/fixtures/v4_complete_cases.json` (600 случайных готовых +
16 указанных: нулевой хан, таняо+дора без пинфу, чиитоицу с ака и без,
кокуши, двойная рука, суанко-против-чиницу (макс. разложение), рюисо, дайсанген,
суанко, **чинрото-чиитоицу** (зафиксировано: в игре нет яку-мана у чиитоицу),
дорогая пара, ака в поне, итцу+дора, сансёку додзюн, чиитоицу+2 доры +
3 указанных с ура-дорой, в том числе чистые девять врат с ура-дорой 1m —
проверка, что якуман урадоры не получает) — сверяются хан, тир, база,
структуры, плоские яку и итог `evaluateCompleteHand(tiles, ctx)`. Фикстура
пересчитывается:

```powershell
py stats/tools/gen_complete_reference.py --random 600 --deals 300000000
```

(фазза 200k рук сверяет `complete_type` с независимым эталонным портом
`isWinningHand` перед генерацией).

Эталон считается тем же кодом, что тело цикла в `simulate_chunk`,
но руками из фикстуры. Модель ака в обеих реализациях одна:
в стене по одному красному тайлу на масть; в фикстурах пятёрка масти
помечается красной с вероятностью n/4, и хан даёт каждый красный вид,
оставшийся в победной руке (в игре — конкретные тайлы `'0m'/'0p'/'0s'`,
в статистике — пометки `par[P_AKA_M/P/S]`).

Масштабирование по процессам нелинейное (12 процессов ≈ 6.5 ядра: упирается в
память/кэш), поэтому ориентиры режима 1: 1e7 ≈ 12 мин, 1e8 ≈ 2 ч, 1e9 ≈ 19 ч;
режима `yaku`: 1e8 ≈ 10 мин, 1e9 ≈ 1.6 ч (в 12 раз быстрее режима 1);
режима 2: 1e9 ≈ 30 с, 1e10 ≈ 5 мин; режима `design`: 1e8 ≈ 2 ч.
Оптимизации режима 1: `analyze` вызывается только для сбросов с шантеном ≤ 2 и
только на нужной глубине (`lim = шантен + 1`, тенпай ~21 мкс вместо ~1135);
разбиение — DP по мастям (`partition_v4`) вместо рекурсии (~78 мкс на руку
против ~146). Отсев «не готова» в режиме 2 — два reject-прохода до DFS;
хан/структуры/яку считаются только на ~3·10⁻⁶ готовых.
Режим `yaku` — это режим 1 минус шантены и всё, что от них зависит (тир, база,
доры, ака, риичи, урадоры): остаются перебор сбросов, `partition_v4` и
`detect_yaku_v4` (~39 мкс на руку), плюс отсев сбросов, которые не могут выиграть
по яку (см. «Режим 5»).
