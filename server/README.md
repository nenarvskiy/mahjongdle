# mahjongdle-server

API для [mahjongdle](../README.md): **вход через Google** и **таблица рекордов
дня**. Сервер сам раздаёт и статический фронтенд (один origin, один порт),
поэтому всё можно держать на одной машине — даже без домена (Tailscale
Funnel, см. ниже) — или классически: статика на GitHub Pages/Vercel/Netlify +
API на своём сервере (Render / VPS / Fly / Docker, что угодно, где Node 24+).

## Как это работает

```
Браузер (статика)                        server/
─────────────────                        ─────────
1. Кнопка «Войти через Google»
   (Google Identity Services, popup)
2. Google отдаёт ID-токен (JWT) ────────▶ 3. POST /api/auth/login {idToken}
                                           проверка подписи (JWKS Google),
                                           issuer, audience = client ID
                                           (google-auth-library)
4. ◀────────────────────────────────── {token: сессия JWT 30 дней, user}
5. Сессия в localStorage, заголовок Bearer
6. POST /api/scores {date, score}   ────▶ upsert: лучший на (user, date)
7. GET  /api/scores/:date           ────▶ публичный топ-10 дня
```

* Токен Google проверяется **на сервере** — клиенту доверия нет.
* Сессия — собственный JWT HS256 (node:crypto, без jsonwebtoken), 30 дней.
* База — `node:sqlite` (встроена в Node 24), один файл `data/leaderboard.db`.
  Две таблицы: `users` (id = Google `sub`) и `scores` (PK: user+date).
* На сервере хранится **лучший** результат игрока за день; при равенстве очков
  выше тот, кто записался раньше.
* В таблицу идёт только «рука дня» — та, что сгенерирована кнопкой
  «Сгенерировать руку» (раз в день; до генерации на экране 14 рубашек,
  кнопка затем неактивна до следующего дня, рука хранится в localStorage
  браузера).

## Эндпоинты

| Метод | Путь | Тело | Ответ |
|---|---|---|---|
| POST | `/api/auth/login` | `{idToken}` | `{token, user{id,email,name,picture,role}}` |
| GET | `/api/me` | — | `{user (с role)}` |
| POST | `/api/scores` | `{date, score, discarded?, tiles?}` | `{score, isBest, rank}` |
| GET | `/api/scores/:date?limit=N` | — | `{date, rows:[{id,name,picture,score,discarded}]}` |
| GET | `/api/roles` | — (только admin) | `{admin:[email], test:[email]}` |
| POST | `/api/roles` | `{email, role: admin\|test\|player}` (только admin) | новый файл ролей |
| POST | `/api/events` | `{mode, kind:'hand', payload}` (блок посчитанной руки; анонимы тоже) | `{id}` |
| PATCH | `/api/events/:id` | `{payload}` (пересчёт той же руки; владелец) | `{id, payload}` |
| POST | `/api/events/:id/report` | `{text}` (жалоба к блоку; владелец) | `{id, report}` |
| GET | `/api/events?reports=1&limit=` | — (только admin) | `{rows:[…]}` — новые сначала |
| GET | `/api/me/yesterday?date=YYYY-MM-DD` | — (сессия) | `{date, hand, kans, oldScore, newScore, changed, dayKanCount, recalculated}` |
| GET | `/api/daily/kans?date=YYYY-MM-DD` | — (публично) | `{date, kans:[{name,kanCount}] (≤10 строк), total (точная сумма, 0.7.1)}` |
| GET | `/api/admin/backup` | — (только admin) | `{configured, repo, file, branch, lastPushAt, lastPushError, dbSize}` |
| GET | `/health` | — | `{ok:true}` |

`date` — `YYYY-MM-DD` (день по Москве, тот же, что у фронтенда в
`daily-context.js`). `score` — целое ≥ 0. Все ошибки — JSON `{error}`.

## Роли: admin / test / player

* **player** — по умолчанию: рука дня (1 в день, идёт в таблицу рекордов).
* **test** — + тестовый режим: неограниченные руки и ручные руки
  13/14 тайлов с теми же правилами оценки; **ничего из тестового режима не
  попадает в таблицу, статистику и будущие достижения** — фронтенд в этом
  режиме просто не вызывает `POST /api/scores`.
* **admin** — всё как у test + панель «Роли (admin)» в игре.

Списки — в файле **`server/config/roles.json`** (НЕ в корневом `config/` —
корневой раздаётся браузеру):

```json
{
  "admin": ["вы@example.com"],
  "test": ["тестер@example.com"]
}
```

* Файл перечитывается **на каждый запрос** (hot-reload): владелец правит его
  на сервере — роль применится при следующем входе/опросе, **без рестарта**.
  Роль возвращается в `/api/auth/login` и `/api/me`, а фронтенд при загрузке
  страницы подтягивает актуальную роль (`refreshMe`).
* Управлять списками можно и без SSH: кнопка «Роли (admin)» (только admin) —
  добавление email + роли, «убрать» (= player).
* `player` — это «не в списках», отдельного списка нет.
* **Аудит L3 — роли без файла в публичном репозитории.** Реальные
  admin-email не должны лежать в публичном GitHub. Вместо файла — env-переменная
  **`ROLES_JSON`** (JSON той же структуры):

  ```
  ROLES_JSON={"admin":["вы@example.com","второй@example.com"],"test":["тестер@example.com"]}
  ```

  * При старте `server/index.js` пишет её в `os.tmpdir()/mahjongdle-roles.json`
    и работает с этим файлом (hot-reload и панель ролей работают как обычно —
    изменения живут в tmp-файле **до следующего деплоя**, источник правды — env).
  * Приоритет: `ROLES_FILE` > `ROLES_JSON` > файл по умолчанию
    (`server/config/roles.json`).
  * Если в итоге **нет ни одного admin** — при старте печатается предупреждение
    (панель ролей и ре-ишю рук будут недоступны).

## Сквозной лог (`events`)

Игра пишет на сервер всё важное (таблица `events` в `data/leaderboard.db`):

* **`hand`** — один блок = одна **посчитанная** рука: тайлы, условия (ветра,
  дора, ура, день), режим (`daily` / `test`) и **счёт с полной разбивкой
  «что за что»** (база, структуры, каждый яку с очками, потенциал).
  Если игрок нажал «Сообщить об ошибке», жалоба лежит в том же блоке
  (`payload.report = {text, ts}`) — отдельной записи-жалобы нет.
  Просто сгенерированная рука без счёта в лог **не пишется** (сервер требует
  `payload.total`), а пересчёт при смене условий/другом сбросе обновляет
  тот же блок (`PATCH`), не создавая новый.

Данные игрока (id/email/имя) сервер подставляет **из своей сессии** —
в теле запроса только игровые данные; анонимные руки логируются с
`user_* = null` («аноним»). `POST /api/events` открыт (в т.ч. анонимам), но ограничен: `mode` ∈
daily/test, `kind` = `hand`, обязателен `payload.total`, размер payload
≤ 20 КБ, rate-limit 60 событий/мин на IP. Правка блока (`PATCH`) и жалоба —
**только владелец** блока (иначе 404). Чтение — `GET /api/events` **только
admin**; `?reports=1` — лишь блоки с жалобами.

Админ смотрит всё в игре: кнопка **«Логи и жалобы»** — карточки с
таймом, игроком, режимом, рукой (тайлами) и разбивкой счёта; жалобы —
с текстом.

## Настройка Google Cloud Console

1. [console.cloud.google.com](https://console.cloud.google.com) → ваш проект
   (или новый).
2. **APIs & Services → OAuth consent screen**:
   * User Type: **External** (Internal — только если у всех аккаунты вашей
     доменной организации).
   * Заполнить приложение: имя (например «Mahjongdle»), email контактный,
     домен.
   * Scopes: **достаточно базовых** (email, profile) — их GIS запрашивает
     сам; добавлять scope не нужно.
   * Пока статус **Testing**, в него могут войти только аккаунты из
     «Test users» (добавьте себя) — и токен живёт 7 дней. Для публичной
     таблицы: **Publish app** (Review app → Publish).
3. **APIs & Services → Credentials → Create credentials → OAuth client ID**:
   * Type: **Web application**.
   * **Authorized JavaScript origins** — домены фронтенда:
     * dev: `http://localhost:3000` (или порт локального сервера статики),
     * прод: `https://ваш-домен.github.io`, `https://mahjongdle.example.com`…
   * **Authorized redirect URI** — не нужен (GIS с ID-токеном не редиректит).
   * Скопировать **Client ID** (`...apps.googleusercontent.com`).

## Локальный запуск

Один процесс отдаёт и API, и игру (один origin — CORS не нужен):

```powershell
cd server
npm install

# переменные окружения (или server/.env + node --env-file=.env index.js)
$env:GOOGLE_CLIENT_ID='1234...-abcdefgh.apps.googleusercontent.com'
$env:SESSION_SECRET='длинная-случайная-строка'   # ≥ 16 символов:
#   node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"
$env:PORT='3000'
npm start
```

Открываете **http://localhost:3000** — это сама игра (API:
`http://localhost:3000/health` → `{"ok":true}`). В **`config/auth.json`**
(корень проекта) вписать client ID:

```json
{
  "googleClientId": "1234...-abcdefgh.apps.googleusercontent.com",
  "apiBaseUrl": ""
}
```

Пустой `apiBaseUrl` = API на том же origin, что и игра. После этого в шапке
появится кнопка «Войти через Google», а под результатом — «Таблица дня».
Пока `googleClientId` пустой — функция выключена, игра работает как раньше.

`STATIC_DIR` — каталог фронтенда (по умолчанию корень проекта);
`STATIC_DIR=off` — только API, когда фронтенд раздаётся отдельно
(`npx serve .` в корне): тогда в `config/auth.json` `apiBaseUrl` = адрес
сервера, а `CORS_ORIGINS` = origin фронтенда.

## Публичный сайт без домена (Tailscale Funnel)

Чтобы в игру можно было играть с любого устройства по HTTPS, не покупая домен:

1. Поставить [Tailscale](https://tailscale.com) на машину, где крутится сервер
   (хватает бесплатного личного плана), залогиниться в tailnet.
2. Запустить сервер на порту 3000 (как в «Локальном запуске»).
3. `tailscale funnel 3000` — Tailscale публикует порт по HTTPS на адресе
   `https://<имя-машины>.<ваш-tailnet>.ts.net` (точный адрес — в выводе команды).
4. Этот адрес добавить в **Authorized JavaScript origins** Google Cloud Console.
5. Ссылку передать тестировщикам; `apiBaseUrl` остаётся `""` (один origin).

Ограничения: машина должна быть включена и не уснуть — это тестовый хостинг.
Для постоянного — тот же код на VPS (Oracle/GCP free tier, работает постоянно)
+ Tailscale Funnel: адрес по-прежнему `*.ts.net`, домен не нужен. Кнопка
Google требует HTTPS или localhost — именно это и даёт Funnel; по локальному
IP (`http://192.168.x.x`) кнопка работать не будет.

### Несколько пользователей

Пока статус приложения **Testing**, заходить могут только аккаунты из
«Test users». Чтобы пускались любые люди: **Review app → Publish app** —
с базовыми скоупами (email, profile) они нечувствительные, публикация
проходит мгновенно, без верификации.

## Деплой

### Сервер

Любой хостинг с Node 24+ и постоянным файлом (нужен для SQLite):

* **Render / Fly.io / Railway** — репозиторий + start command
  `npm --prefix server start` (или `cd server && npm start`), переменные
  окружения как выше, volume на `server/data` (Render: Disk).
* **VPS** — systemd / pm2: `pm2 start server/index.js --name mahjongdle`.
* **Docker** — см. `server/Dockerfile`.

### Постоянное хранение (чтобы ничего не «слетало»)

База — один файл SQLite. **На free-инстансе Render без подключённого диска
файл живёт в эфемерной ФС контейнера и СТИРАЕТСЯ при каждом деплое.**
Тогда «слетают» таблица дня, руки игроков и их история. Сервер при старте
в `production` пишет предупреждение в лог, если `DB_FILE` не лежит на
`/opt/data/`.

Два способа это решить:

### Вариант A: бэкап в приватный GitHub-репозиторий (бесплатно, без диска)

Сервер сам шлёт `leaderboard.db` в приватный репо (GitHub Contents API):
после каждого изменения (проверка раз в минуту) — commit; при старте
свежего инстанса (после деплоя), когда локальной БД нет, — восстановление
из последнего commit. Потеря в худшем сценарии — секунды-минуты между
последним бэкапом и деплоем.

Настройка:

1. GitHub → **New repository** → имя `mahjongdle-data`, **Private**,
   галка **Add a README file** (создаёт ветку `main`).
2. GitHub → **Settings → Developer settings → Fine-grained personal
   access tokens → Generate new token**: доступ только к репо
   `mahjongdle-data`, permission **Contents: Read and write**.
3. Render → сервис → **Environment** → две переменные:
   * `BACKUP_GITHUB_REPO=nenarvskiy/mahjongdle-data` (ваш owner/repo),
   * `BACKUP_GITHUB_TOKEN=<токен из п. 2>`.
   Необязательные: `BACKUP_FILE` (по умолчанию `leaderboard.db`),
   `BACKUP_BRANCH` (по умолчанию `main`),
    `BACKUP_WATCH_INTERVAL_MS` (интервал проверки изменений, по умолчанию 60000).
4. Redeploy. В логах при старте: `backup: …`; статус —
   `GET /api/admin/backup` (только admin): время последнего commit,
   ошибки, размер файла.

Ограничения: зависит от доступности GitHub API (ошибка бэкапа логируется,
игра при этом работает как обычно); коммиты копятся в истории репо
(один за каждые изменения БД — для нашей нагрузки это единицы в день).

Защита от затирания истории (аудит F5/K1):

* Файлы крупнее ~1 МБ GitHub Contents API не возвращает в body
  (`content: null`) — pull добирает копию сырьём по `download_url`.
* Если pull при старте не удался (сеть/5xx), удалённое состояние
  **неизвестно** — push **заблокирован целиком**, не по числу строк:
  свежий инстанс не должен затирать хорошую копию в репо (раньше guard
  считал строки по всем таблицам, и «пустая» БД с гостевыми событиями
  пушилась, затирая историю). Разблокирует push только успешный pull при
  следующем старте (рестарт/деплой) или успешный push; до этого данные
  копятся локально, и в логах — предупреждение (не чаще раза в 15 минут).
  На практике: если GitHub лёг на минуту — рестарт инстанса чинит.
* `remoteKnown = true` также при пустом репо (`no-copy` — перекрывать
  нечего) и при непустой локальной БД на старте (постоянный диск —
  локаль не старше последней успешной копии).

Важно: БД в режиме WAL — записи копятся в файле `leaderboard.db-wal`,
а главный файл меняется только при чекпоинте. Поэтому watcher считает
«изменение» по mtime **всех** файлов БД (`db`, `-wal`, `-shm`), а не только
главного (иначе свежие счёта не уезжали в репо до чекпоинта и терялись
при следующем деплое).

### Вариант B: подключённый диск Render ($0.90/мес за 1 ГБ)

1. Панель Render → ваш сервис → **Disks** → **Attach New Disk**:
   mount path **`/opt/data`**, размер 1 ГБ (хватит с запасом).
2. **Environment** → добавьте `DB_FILE=/opt/data/leaderboard.db`.
3. Сохраните (это задеплоит сервис). С этого момента файл живёт на диске
   и переживает деплои и перезапуски — данные не слетают.

Варианты можно комбинировать (диск + бэкап в репо — двойная страховка).

> При первом старте с новым/чистым хранилищем база пустая (таблица
> начнётся заново) — это нормально. Если хочется сохранить старую таблицу,
> скопируйте `leaderboard.db` до переключения и перезапустите.

Обязательно:

* **Постоянный файл БД** (см. выше) — иначе рейтинг и руки сбрасываются
  при каждом деплое.
* `SESSION_SECRET` — случайный, не коммитится.
* HTTPS (Render/VPS — через TLS-сертификат; фронтенд на https не будет
  ходить на http-API; Tailscale Funnel — HTTPS из коробки).
* Origin, на котором открыта игра, добавить в Google Cloud Console
  **Authorized JavaScript origins** (домен / `*.ts.net` / `http://localhost:3000`).
* `CORS_ORIGINS` — только если фронтенд раздаётся отдельно от сервера
  (`STATIC_DIR=off`); при общем origin он не нужен.
* `config/roles.json` — файл списков ролей. На хостинге с эфемерным диском
  (Render без volume) правки «панелью ролей» живут, пока жив контейнер:
  положите `server/config` на volume рядом с `server/data` либо держите
  списки в репозитории/секретах и копируйте файл при деплое.

### Фронтенд (статика)

* **GitHub Pages** — опубликовать корень репозитория (actions или
  Settings → Pages). В `config/auth.json`: `apiBaseUrl` = URL сервера,
  `googleClientId` = client ID; домен Pages добавить в authorized origins.
* **Vercel / Netlify** — import репозитория, build command не нужен
  (pure static), publish directory = корень.

> Альтернатива «своему серверу»: тот же код легко превратить в serverless
> функцию Vercel/Netlify, но SQLite там не подойдёт (нужна Postgres/Supabase)
> — это уже другой вариант, здесь он не поддерживается.

node test/server.test.js          # вход, сессии, валидация, ранги, CORS, роли, лог,

В тестах Google подменяется заглушкой (сеть не нужна). Реальная проверка
`google-auth-library` (JWKS) происходит на живом сервере: поддельный
ID-токен получает 401.

## Ночной пересчёт (кандоры и ура-доры)

Мёртвая стена дня — 10 тайлов, одинаковая для всех игроков и зависящая только
от `dayKey` (`createDeadWall` в `src/daily-context.js`). Все доры дня берутся
из стены (0.6.25): [0] дора-индикатор, [1] ура-индикатор, [2]/[4]/[6]/[8] —
кан-доры 1..4, [3]/[5]/[7]/[9] — кан-уры 1..4. Один тайл каждого вида стены
отложен (в раздачу не попадает, как индикаторы в реально риичи), остальные 3
копии вида в обороте. Таблица `day_hands` хранит руку игрока на момент
сдачи (14 тайлов, 13 после сброса, объявленные каны, контекст дня).

При первом за день запросе `GET /api/me/yesterday` сервер пересчитывает
вчерашние руки (один раз, флаг `recalculated`). Доры открываются **для всех
игроков, по канам дня в целом** (все игроки, `dayKanCount`), а не по канам
каждой руки:

* **ура-доры**: 1 базовая (ура-индикатор дня — 2-й тайл стены) + по одной
  кан-уре за каждый кан дня (макс. 1 + 4 = 5);
* **кан-доры**: по одной за каждый кан дня, **без базовой** (макс. 4 —
  столько канов, сколько может быть в руке; тайлы 3, 5, 7, 9 стены);
* базовая дора пересчёта берётся из контекста, сохранённого при сдаче руки
  (`day_hands.day_ctx`): день, сданный по старой схеме (до 0.6.25), остаётся
  со своим публичным индикатором, ура и кан-доры таких дней выводятся уже по
  новой стене;
* в живой игре (до полуночи) ура-доры и кан-доры ни у кого не считаются и
  нигде не видны — только базовая дора и ветра;
* готовые руки пересчитываются через `evaluateCompleteHand`, остальные —
  через `evaluateHand` с канами как фиксированными понами;
* таблица дня обновляется, рейтинг может измениться.

Фронтенд показывает полноэкранное окно «Вчера»: рука, сброшенный тайл,
открывшиеся ура-доры и кан-доры, старый/новый счёт (если изменился).
Ответ `GET /api/me/yesterday` несёт `dayKanCount` — суммарные каны дня.

## Контракт руки дня (аудит 0.6.26: K2, H1–H4)

Сервер не доверяет клиенту в происхождении руки — счёт считается только от
тайлов, выведенных из **черновика** (руки, выданной игроку):

* **Черновик — один на день** (`POST /api/me/hand`, при генерации). Повторная
  POST → **409**: «перевыпуск до нужного расклада» закрыт (H4). Замена —
  только `POST /api/admin/hand/reissue`.
* **Результат сдаётся только против черновика** (`POST /api/scores`):
  без черновика → 400 (K2: раньше произвольная `complete`-рука давала очки).
  Мультиконтр-проверка: отправка не содержит меньше выданного тайла, на каждый
  кан — ровно один добор, кан — на 4 тайла черновика.
* **Готовая рука**: `hand` обязан мультимножеством равняться `tiles` (14),
  которые, в свою очередь, выводятся из черновика (K2). Счёт — от `tiles`.
  Готовая рука **после кана** идёт в пон-форме: `tiles` = 14 (пон кана
  включён), 4-й тайл кана сервер добавляет в валидацию (H1).
* **Физика**: не больше 4 копий любого тайла (и ≤ 3 для тайлов мёртвой
  стены) — проверяется и в черновике, и в отправе.
* **Каны — на сервере** (`PATCH /api/me/hand/:date {kans}`): кан объявляется
  до сброса, прогресс хранится в `day_hands.kans` (H2). Клиентская синхронизация
  кан-осознанна: локальный пост-кан прогресс новее серверного → сохраняется
  (и дособылается на сервер), каны те же → локальный добор не перекладывается,
  серверный кан на чистом устройстве → применяется к черновику (вынос 4 + добор).
  После сдачи результата PATCH → 409 (каны живут в результате).
* **Приватность** (`GET /api/me/hands`, H3): в `day_ctx` строки **за сегодня**
  вырезаны ура-индикаторы/ура-тайлы/мёртвая стена (не открылись до полуночи);
  прошедшие дни — полный ctx (базовая дора старых схем + ветра).

## Изменения 0.7.0 (аудит M/L)

* **M1 — бэкап: запись во время upload не теряется.** `pushNow` фиксирует
  `mtime` БД **до** копирования; если после успешного upload БД изменилась
  (запись во время PUT), маркер остаётся старым и запускается повторный
  push через `retryDelayMs` (по умолчанию 1500 мс) — копия в репо догоняет
  локальную. Раньше `lastPushMtime` записывался после upload: запись,
  сделанная во время PUT, «учитывалась» маркером, но не попадала в копия,
  и следующий `tick` её не пушил.
* **M4 — нулевая «готовая» рука больше не создаётся.**
  * `POST /api/scores` с `complete: true` обязан нести `hand` из 14 тайлов,
    совпадающий с `tiles` (валидация в `recalc.js`); пустой/отсутствующий
    `hand` — 400.
  * `complete` с итоговым счётом 0 — 400 `«готовая рука не выигрышная»`
    (база готовой руки в v4 ≥ 5 400 000, поэтому 0 — это не 4 сета + пара).
    Нулевая строка в `scores` не создаётся.
  * `getFixedResult` теперь считает **любую** строку в `scores` результатом
    (включая `score = 0` — legacy-строки старой версии клиента): повторная
    отправка возвращает зафиксированный результат 200, а не падает 500 на
    `UNIQUE constraint`.
  * Вставка в `scores` — `ON CONFLICT ... DO UPDATE` (upsert): гонка двух
    вкладок обновляет строку, а не роняет 500.
* **L1 — ограничение размера тела.** Ошибка `entity.too.large` от
  `express.json` (тело > 64 КБ) — 413 `«тело запроса слишком большое»`,
  а не 500.
* **L2 — окно «Вчера» не показывает черновик.** Черновик (рука
  сгенерирована, но не сдана: нет ни сброса, ни готовности, ни очков) —
  не сыгранная рука: `GET /api/me/yesterday` возвращает `hand: null`,
  а полночный пересчёт черновик пропускает.
* **L3 — роли через env `ROLES_JSON`** (см. раздел «Роли»): реальные
  admin-email можно вынести из публичного репозитория в переменные
  окружения; файл по умолчанию становится примером.

## Изменения 0.7.1 (аудит 2026-10-27: №1–№9)

* **№1 — тестовый набор не зависит от календарной даты.** Тесты с каном
  (F2-7, H1) собирают кан-руку из живых тайлов дня (`kanWinningHand`):

  `1m` сидел в стене и `npm test` падал ложно (127/129).
* **№2 — 5-я копия тайла при синхронизации 2+ канов.** Логика вынесена в
  чистый модуль `src/hand-sync.js` (`applyServerKansToDraft`, покрывается
  тестами `test/daily-hand-sync.test.js`); все доборы — ОДНИМ вызовом
  `drawHand(N)` из одной перемешанной стены: доборы различны, и ни один
  из них не входит в черновик (5-я копия вида невозможна).
* **№3 — кан = фиксированный пон и в пути готовой руки.**
  `evaluateCompleteHand` с каном проверяет `isWinningHandWithKans`
  (после пона кана: `4 − каны` сета + пара), а `evaluateStandard`
  рассматривает только разложения, где пон кана цёл. Без фикса готовая
  рука могла «выигрывать» только через разложение, ломающее пон кана
  (вероятность в игре ~10⁻⁷, но модель была несогласована с шантеном и
  ожиданиями). Клиент и сервер используют один модуль — сдача и ночной
  пересчёт согласованы.
* **№4 — сумма канов дня без `LIMIT 10`.** `sumDayKanCount(db, date)` —
  точная сумма по всем строкам дня: `GET /api/me/yesterday`

  /api/daily/kans` (новое поле `total`) больше не обрезаются при 10+
  игроках с каном. Публичный список имён остаётся ограниченным 10
  строками (только атрибуция для тултипов); клиент берёт `total`.
* **№5 — тестовый режим: добор после кана без 5-й копии.** `exclude` в
  `drawHand` (текущая рука + тайлы объявленных канов) — как в M2.
* **№6 — фиксация результата — явная.** PATCH канов закрыт наличием

  строку, если в `scores` уже есть результат. Смена правил (например,
  блок «кан» → 0) больше не «открывает» прогресс канов после сдачи.
* **№7 — `apiBaseUrl` можно оставить пустым.** Пустой `apiBaseUrl` в

  (игра и API на одном origin) работает без правок, локальный dev-сервер

* **№8 — операционное:**
  * **retention `events`**: `pruneEvents(db)` (30 дней) вызывается при

  * Известные остатки (не закрыты): лимиты в памяти (сброс при рестарте),

* **№9 — мелочи:** `where.mjs` получил пропущенный импорт `writeFileSync`;
  из `src/kans.js` удалены мёртвые API `hasKan`, `countKans`,

## Клиент 0.7.3 (авторетраи при «холодном старте» Render)

На Render free tier инстанс спит после ~15 минут без трафика; при
пробуждении/рестарте/деплой (10–30 с) прокси отдаёт на POST **405**,
иногда 5xx, а на GET — HTML-страницу «spinning up» вместо JSON. Игрок
видел «Не удалось сохранить результат: HTTP 405» — хотя результат ещё
можно было отправить. Теперь `api()` в `src/auth.js` (единая обёртка
всех запросов) при 405/5xx, сетевой ошибке или HTML-ответе **ждёт и
повторяет** (задержки 3/7/12/15 с — до ~37 с, накрывает типичный
холодный старт); ошибки пользователя (400/401/409) повторов не ждут.
Тестовый хук `setApiRetryDelays` + 4 теста (`test/auth-retry.test.js`).

## 0.7.4 (инцидент GitHub Pages + backfill пропущенного результата)

**Инцидент 2026-10-27…29.** Игра дублируется на GitHub Pages
(`https://nenarvskiy.github.io/mahjongdle/` — статическая копия того же
репозитория), и игрок играет именно там. Сделка №7 из 0.7.1 («пустой
`apiBaseUrl` = origin страницы») для этой копии означала: все API-запросы
шли на `nenarvskiy.github.io/api/...` — GitHub Pages отвечает только
404/405 (статика). Игрок видел «HTTP 405» на сохранение и «сервер
недоступен» на истории; ретраи 0.7.3 повторяли запросы в никуда.
Причина — 0.7.1, который перевёл коммит-конфиг на пустой `apiBaseUrl`
(раньше там был явный `https://mahjongdle.onrender.com`).

* **`config/auth.json` возвращён к явному `apiBaseUrl:
  "https://mahjongdle.onrender.com"`.** Обе копии работают: на Render
  страница и API на одном origin (явный URL = тот же origin), на GitHub
  Pages — кросс-домен на Render (CORS_ORIGINS в окружении Render
  разрешает `https://nenarvskiy.github.io` — проверено preflight:
  `access-control-allow-origin` эхо). Локальный dev по-прежнему
  подменяет конфиг (dummy clientId + пустой `apiBaseUrl` → origin).
* **`POST /api/admin/score/backfill {date, hand, discarded, kans?}`**
  (только admin/test): восстановление ПРОПУЩЕННОГО результата, когда
  рука была сыграна, но отправка до сервера не дошла. Принимаются
  прошедшие и СЕГОДНЯШНЯ даты (будущее нельзя); обычный `POST
  /api/scores` в этом случае не работает — он требует зафиксированный
  черновик (K2), а черновик как раз и не дошёл. `hand` — 14 выданных
  тайлов (черновик на сервере НЕ требуется); сброшенный тайл и каны
  проверяются как в обычной отправке (id, мёртвая стена ≤3 копии,
  численность, каны — только на тайлах руки). Счёт — серверный:
  прошедший день — «полночная» формула (`recalcScore`: ура + кан-доры
  по канам дня) + `recalculated=1` (ленивый пересчёт не тронет);
  сегодняшний — «дневной» (`computeDayScore`, без ура) +
  `recalculated=0` — ленивый полночный пересчёт добавит ура/кан-доры,
  как у обычной сдачи. Тест в `test/server.test.js` («0.7.4 backfill»).

  их закрытыми, как в игре (`renderClosedKan`: крайние тайлы рубашкой,
  центральные два открыты) — мелкими, над рукой. Свой кан до
  подтверждения PATCH берётся из `declaredKans`.

  «Вчера»: рубашка-тайл-тайл-руба́шка (закрыты первый и последний).
  Готовая рука — без изменений (пон виден в 14 тайлах, отдельно — 4-й
