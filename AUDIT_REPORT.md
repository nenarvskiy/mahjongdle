## Высокая важность

### F1. Повторная отправка результата: нет серверной политики и рассинхронизация слоёв

Правило продукта: один результат в день, повторная отправка разрешена только admin/test. Ниже — что код делает при повторной отправке и где это ломается.

#### F1.1. «Только admin/test» сейчас не enforced

`POST /api/scores` не вызывает `roleFor` ([server/app.js:267-269](server/app.js#L267-L269)) — проверяется только токен, роль не используется. Обычный игрок может отправить результат повторно:

- **Перезагрузка страницы.** `render` → `maybeSubmitScore` снова отправляет тот же счёт. Равный счёт данные не портит, но `isBest` ложен и UI пишет «у вас уже был лучший результат» для единственного же результата ([src/main.js:366-368](src/main.js#L366-L368)).
- **Две вкладки/два устройства.** Обе вкладки загрузили одну руку; синхронизации на `focus`/`visibilitychange` нет (только смена дня, [src/main.js:312-314](src/main.js#L312-L314)). В каждой можно сбросить разный тайл — две разные попытки с одного аккаунта.
- **Гость → логин.** Гость сыграл и вошёл: `state.daily` уже `true`, синхронизация с сервером пропускается ([src/main.js:858-863](src/main.js#L858-L863)), гостевая рука уходит на сервер — вторая попытка, если на сервере результат уже был.
- **Старый клиент.** Проект сам эмулирует сценарий: [test/server.test.js:658-689](test/server.test.js#L658-L689) — пользователь `sub-2` **без роли** отправляет 2000, затем 1000 с `kans: []` («перезагрузка страницы старым клиентом»); тест ожидает `200` и проверяет только каны. Повторная отправка от обычного игрока уже зафиксирована в тестах как нормальный сценарий.

Если политика «только admin/test» — её должен проверять сервер, а не клиент.

#### F1.2. Слои расходятся: нет единой политики last-wins / best-of

При повторной отправке с худшим счётом:

- `scores` = **последняя** отправка — `UPDATE` пишется всегда ([server/db.js:103-106](server/db.js#L103-L106));
- `day_hands.score` / `complete` = **максимум** — `CASE WHEN excluded.score > day_hands.score` ([server/db.js:270-272](server/db.js#L270-L272));
- `day_hands.hand` / `tiles` / `kans` / `day_ctx` = **последняя** отправка, без условий ([server/db.js:265-269](server/db.js#L265-L269));
- ответ `score` / `rank` / `isBest` = **максимум** ([server/db.js:113-121](server/db.js#L113-L121));
- `created_at` = время первого/лучшего, не последнего ([server/db.js:99-101](server/db.js#L99-L101)) — ломает тай-брейк при равных очках;
- UI — «у вас уже был лучший результат» ([src/main.js:366-368](src/main.js#L366-L368)); docs — «там хранится ЛУЧШИЙ» ([src/auth.js:170](src/auth.js#L170)); тест — «хуже — не обновляет» ([test/server.test.js:119](test/server.test.js#L119)), при этом БД обновляет; комментарий `db.js` — «время записи обновляем только при новом рекорде» ([server/db.js:99-101](server/db.js#L99-L101)).

Это не last-wins и не best-of, а гибрид: при любой политике одна из сторон врёт. Тест [test/server.test.js:112-131](test/server.test.js#L112-L131) проверяет только тело ответа, а не БД; тест таблицы (строка 133) проходит, потому что следующая отправка 200 случайно «ремонтирует» строку.

#### F1.3. Понижение после ночного пересчёта не откатывается — навсегда

Воспроизведено локально, пользователь без роли, рука за `2026-10-22`:

```
first 1000  → 200 {score:1000, isBest:true, rank:1}
recalc      → 200 {oldScore:1000, newScore:5400995, recalculated:true}
              day_hands.score = 5400995, scores.score = 5400995, recalculated = 1
second 10   → 200 {score:5400995, isBest:false, rank:1}   ← API «не согласен» с БД
              scores.score = 10, day_hands.score = 5400995, recalculated = 1
leaderboard → 10
yesterday   → 200 {oldScore:5400995, newScore:5400995, changed:false, recalculated:true}
              scores.score остаётся 10
```

Механика: `upsertScore` пишет 10; `upsertDayHand` оставляет максимум 5 400 995 и `recalculated=1`, потому что `10 > 5 400 995` ложно ([server/db.js:270-272](server/db.js#L270-L272)); `/api/me/yesterday` видит флаг и не пересчитывает ([server/app.js:355](server/app.js#L355), [357](server/app.js#L357)); `setScoreValue` ([server/db.js:393-396](server/db.js#L393-L396)) больше не вызывается. В публичной таблице — 10, а ответ API, ранг и `day_hands` — 5 400 995; строка зафиксирована в противоречии.

Это сценарий не только «админ вручную»: вкладка, открытая через полночь, может отправить вчерашний результат уже после пересчёта (до автоперезагрузки по смене дня — до ~60 с). До пересчёта то же самое: `scores` = худшее, `day_hands` = максимум, ответ = максимум — таблица дня неверна до полуночи, а если вторая отправка с другой рукой, пересчёт закрепляет её.

#### Исправление (варианты политики)

- **A. Первый результат игрока фиксируется; admin/test пересдают** — соответствует описанному правилу, рекомендуемый вариант. В `POST /api/scores`: если для `(user, date)` уже есть результат и роль не admin/test — вернуть существующий результат (200, без записи; перезагрузки не ломаются) или 409. Для admin/test — разрешить overwrite и согласованно обновить `scores` **и** `day_hands` (включая `recalculated=0`, чтобы новый результат прошёл ночной пересчёт), `created_at` — время последней записи, ответ/ранг — от последней записи.
- **B. Last-wins для всех.** Согласованно обновлять `scores` и `day_hands` (счёт, рука, флаг), `created_at` — сейчас; ответ/ранг/UI — от новой записи. Но тогда нужно отдельно запретить вторую попытку с другой рукой/сбросом, иначе «1 результат в день» не выполняется.
- **C. Best-of.** Обновлять только при `score > existing.score` (и `day_hands` только тогда); ответ/ранг — от best; тест читает БД.

При любом варианте: тест [test/server.test.js:112-131](test/server.test.js#L112-L131) дополнить проверкой БД и `GET /api/scores/:date`; сценарий «понижение после `recalculated=1`» — отдельным тестом.

**Уверенность:** высокая (F1.3 воспроизведено; F1.1/F1.2 — код + тест-свидетельство 658).

### F2. Сервер доверяет клиенту во всём, что касается дня

#### F2a. Счёт, рука, каны, дата — без семантической проверки

`POST /api/scores` ([server/app.js:266-324](server/app.js#L266-L324)) проверяет только типы: `date` — формат `YYYY-MM-DD`, `score` — целое `0..10^15`, `tiles` — массив ≤34 строк ≤4 символов, `hand` — ≤14 строк, `kans` — ≤4 строк, `dayCtx` — любой объект. Нет проверки, что дата — сегодня, что рука была выдана сервером, что она не содержит тайлов мёртвой стены, что `kans` реально есть в руке, что `tiles + 3*kans = 13`.

- Любой Google-аккаунт может поставить любой счёт до `10^15` за любую дату (прошлую/будущую) и подменить руку.
- **Фейковые каны влияют на всех:** `listDayKans` ([server/db.js:372-384](server/db.js#L372-L384)) суммирует каны всех игроков, ночной пересчёт открывает по кан-доре/уре за каждый — один игрок может открыть все 4 кан-доры и 4 кан-уры всем.
- Воспроизведено: отправлял руку, которую сервер не выдавал, и произвольный счёт — принято.

Исправление: серверный «сегодня» (MSK) и отказ от других дат; пересчёт счёта на сервере из `hand/tiles/kans` + контекст дня (модуль `recalc.js` уже есть) вместо доверия `score`; валидация руки против мёртвой стены и `kans` против содержимого руки; `dayCtx` — по схеме (см. F2b).

#### F2b. `dayCtx` с `null` навсегда роняет `/api/me/yesterday`

`dayCtx` сохраняется из `/api/scores` и `/api/me/hand` ([server/app.js:320](server/app.js#L320)) без валидации; ночной пересчёт идёт синхронно в цикле без `try/catch` и транзакции ([server/app.js:355-373](server/app.js#L355-L373)).

Воспроизведено: `POST /api/scores` с `dayCtx:{doraIndicators:[null]}` → 200; `GET /api/me/yesterday?date=2026-10-23` → **500** (`TypeError: Cannot read properties of null (reading '0')` — индикатор доры, пустая строка/`null`, доходит до `doraFromIndicator`/`countDora` в [src/daily-context.js](src/daily-context.js)); строки остаются с `recalculated=0`; каждый следующий запрос падает на той же строке. Один игрок блокирует вчерашний пересчёт и экран «Вчера» **для всех** на эту дату.

Исправление: валидировать `dayCtx` при записи (массивы известных id тайлов, ветра из enum) или не хранить клиентский контекст, а выводить из `dayKey`; `try/catch` на строку + лог/отметка битой строки; пачка в транзакции.

#### F2c. Произвольная `date` запускает ночной пересчёт досрочно

`today = req.query.date`, `yesterday = dayBefore(today)` ([server/app.js:342-344](server/app.js#L342-L344)); сверки с реальным «сегодня» нет.

Воспроизведено: рука за `2026-10-22`, `GET /api/me/yesterday?date=2026-10-23` → `newScore: 5400995, recalculated: true` — ура/кан-доры открылись **до полуночи**; затем объявлен кан за `2026-10-22`; повторный запрос → `dayKanCount: 1`, `newScore` тот же, `changed: false`, `recalculated: true` — настоящий полуночный пересчёт этой даты уже не запустится, поздние каны не применятся. Плюс клиент с неверными часами делает это непреднамеренно.

Исправление: «сегодня»/«вчера» считать только на сервере (MSK), клиентскую дату игнорировать или проверять; пересчёт — только для реально прошедшей даты; идемпотентность + транзакция.

**Уверенность:** высокая (всё воспроизведено).

### F4. Кан: 4-я плитка не даёт хан доры, хотя очки за неё начисляются

`doraBonuses` считает ханы доры только по `counts` ([src/evaluate.js:49-65](src/evaluate.js#L49-L65)), а `countHandDoras` добавляет 4-ю плитку кана через `declaredKans` ([src/dora-points.js:23-47](src/dora-points.js#L23-L47)). Для готовой руки с каном `counts` содержит 3 плитки → хан занижен на 1 за каждый кан-дору; красная пятёрка в кане как дора тоже теряется. Строка очков дор при этом считает 4 плитки: [src/scoring.js:114-142](src/scoring.js#L114-L142) (и 13-тайловая [174-176](src/scoring.js#L174-L176)).

Воспроизведено:

```
рука 1m1m1m 234m 567m 234p 9p9p, кан 1m, индикатор 9m
potential.han = 4   (Риичи 1 + Дора ×3)
строка «Доры ×4» = 800
total = 5 406 715, tier Normal
```

Правильно 5 хан → манган: база 56 000 000, total ≈ 56 006 715 — ошибка в 10 раз по базе.

Исправление: передавать `declaredKans`/`kanKinds` в `doraBonuses` и добавлять 4-ю плитку к счётчику дор (или отдельный `doraCounts`); тесты «кан + дора-индикатор» и «красная пятёрка в кане».

**Уверенность:** высокая.

### F5. Бэкап может затереть удалённую БД пустой

При старте: если `pullBackupFile` не удался (таймаут/5xx/сеть), [server/index.js:56-63](server/index.js#L56-L63) продолжает работу, `openDb` создаёт пустую БД. Первый `tick` ([server/index.js:94-103](server/index.js#L94-L103), [server/backup.js:159-164](server/backup.js#L159-L164)) видит `dbMtime() > lastPushMtime (0)` и `pushNow` ([server/backup.js:115-156](server/backup.js#L115-L156)) отправляет пустую БД в GitHub, затирая хорошую копию. На free Render это единственное хранилище — вся история теряется. `pushNow` не проверяет, удавался ли pull; тестовый сценарий «pull упал → push пустой» не покрыт ([test/backup.test.js](test/backup.test.js)).

Исправление: флаг «бэкап восстановлен»; при неудачном pull — не пушить (или ретраить/падать); проверка непустоты БД перед первым push; тест с mock GitHub API (GET 500, PUT 200 → PUT не должен уходить).

**Уверенность:** высокая по коду; runtime-репро не делал.

### F6. Клик по строке таблицы дня не показывает разбивку счёта

Для обычной (не готовой) руки игрок видит руку, сброс, условия и «Очки: N», но не «за что»; для готовой 14-тайловой разбивка работает.

Исправление: добавить `dh.tiles` в SELECT и `tiles: row.tiles` в `openLeaderboardHand` (либо вычислять 13 тайлов из `hand` минус `discarded`).

**Уверенность:** высокая по коду; DOM не прогонял.

### F7. CORS не разрешает `PATCH`

`Access-Control-Allow-Methods: GET, POST, OPTIONS` ([server/app.js:91](server/app.js#L91)); `PATCH /api/events/:id` — [219-238](server/app.js#L219-L238); клиент шлёт `PATCH` при обновлении блока лога ([src/event-log.js:75-80](src/event-log.js#L75-L80)). В кросс-доменной схеме (игра на GitHub Pages, API на Render) preflight для `PATCH` не пройдёт; `updateHandBlock` молча ловит ошибку, блок лога после пересчёта тестовой руки не обновляется — в админском просмотре остаётся старый счёт. В same-origin не проявляется.

Исправление: добавить `PATCH` в allow-methods; тест preflight с `Access-Control-Request-Method: PATCH`.

**Уверенность:** высокая по коду.

### F8. Bug-viewer падает от произвольного payload анонимного события

`POST /api/events` принимает любой payload с конечным `payload.total` (≤20 КБ, лимит 60/мин) ([server/app.js:194-217](server/app.js#L194-L217)). Векторы, проходящие валидацию:

- `remaining: [null]` → `createTileElement(null)` → `tileDisplayName(null)` → `id[0]` → `TypeError` (проверено точечно: [src/tiles.js:78](src/tiles.js#L78) кидает `Cannot read properties of null (reading '0')`);
- `ctx.doraIndicators` — не массив → `.map`/`doraFromIndicator` кидает;
- `breakdown: [{}]` → `row.points.toLocaleString` кидает ([src/bug-viewer.js:137-160](src/bug-viewer.js#L137-L160));
- `ctx.roundWindId` — число → `.toUpperCase` кидает ([165-176](src/bug-viewer.js#L165-L176)).

Одно анонимное событие ломает админскую вкладку «Все руки»: список очищается до рендера, исключение не перехватывается, удалить событие нельзя.

Исправление: серверная валидация payload по схеме и/или `try/catch` на блок с пометкой «битый блок».

**Уверенность:** средне-высокая (код + точечный вызов; DOM не запускал).

### F9. Тестовый режим не считает готовую 14-тайловую руку

`reevaluate`: `full.length === 14` → `phase='choose'`, `score=null` ([src/test-mode.js:271-294](src/test-mode.js#L271-L294)); `evaluateCompleteHand` импортирован, но не вызывается; `phase='complete'` не выставляется нигде (подсказка «Готовая рука» — мёртвая ветка, строки 462-468). Готовая рука оценивается только после сброса как 13-тайловая — в отличие от основной игры.

Исправление: в `reevaluate` при `full.length===14` вызвать `evaluateCompleteHand(full, scoringContext(), declaredKans)`; при непустом результате — `phase='complete'`, `score`, `remaining=full`, без сброса.

**Уверенность:** высокая по коду.
